What actually happens
when your code runs?

Node.js looks single-threaded and instant from the outside. Underneath, four systems hand code back and forth to make asynchronous JavaScript possible: the V8 engine, the Call Stack, libuv, and the Event Loop. This page walks through the theory, then proves it with two live demos.

Part 1 Theory Questions

Answered in plain terms, grouped by the four systems that make Node.js run.

V8 Engine

01What is the V8 Engine?

V8 is Google's open-source JavaScript engine, written in C++ and originally built to power Chrome. Instead of interpreting JavaScript line by line, it compiles JS straight down to native machine code before running it, which is why it's fast enough to run production servers, not just browser tabs.

02Why is the V8 Engine important for Node.js?

Node.js isn't a language of its own — it's a runtime that lets JavaScript run outside a browser. V8 is the part that actually understands and executes the JavaScript. Node wraps V8 with extra C++ bindings (via libuv) so that code can also talk to the file system, network, and OS — things a browser would never allow.

03What is the main responsibility of the V8 Engine?

Parsing, compiling, and executing JavaScript, plus managing memory for it — allocating memory for variables and objects as code runs, and garbage-collecting memory that's no longer in use.

Execution

04What is the difference between Synchronous and Asynchronous execution?

Synchronous code runs top to bottom, and each line blocks the next until it finishes. Asynchronous code lets a slow operation — a timer, a file read, a network request — start in the background, while the rest of the script keeps running immediately. The result of that operation is handled later, through a callback, promise, or async/await, once it's ready.

05What is the Call Stack?

The Call Stack is where JavaScript keeps track of what function is currently running. It's a last-in, first-out structure: every time a function is called, a new frame is pushed onto the stack; when that function returns, its frame is popped off. Node can only run one thing at a time, so whatever sits on top of the stack is exactly what's executing right now.

Event Loop

06What is the Event Loop?

The Event Loop is the mechanism that keeps Node.js running and lets it handle asynchronous work. It continuously checks: is the Call Stack empty? If yes, it looks at the pending queues (timers, I/O callbacks, etc.), takes the next callback that's ready, and pushes it onto the Call Stack to run.

07Why is the Event Loop needed in Node.js?

JavaScript itself runs on a single thread. Without something coordinating background tasks, a slow operation like a network request would freeze the entire program until it finished. The Event Loop is what allows Node to start that operation, move on to other code immediately, and come back to handle the result later — giving single-threaded JavaScript the ability to feel concurrent.

08How does the Event Loop help execute asynchronous code?

It acts as the traffic controller between the Call Stack and the queues that libuv fills in. Once an async task (a timer firing, a file finishing reading) is ready, its callback sits in a queue. The Event Loop only moves that callback onto the Call Stack once the stack is completely empty — so synchronous code always finishes first, and queued callbacks run afterward, in order, one at a time.

libuv

09What is libuv?

libuv is a C library that Node.js is built on top of. It provides the actual Event Loop implementation, plus a thread pool, so that Node can perform operations asynchronously even though JavaScript itself is single-threaded. It's the bridge between JavaScript code and the operating system's async capabilities.

10What types of tasks are handled by libuv?

Timers (setTimeout / setInterval), file system operations, DNS lookups, network I/O, and child processes. Anything that can't be done instantly gets handed to libuv, which runs it in the background (often on its thread pool) and only reports back to the Call Stack, through the Event Loop, once the work is done.

Task 1 — Understanding Asynchronous Execution

console.log("Start");

setTimeout(() => {
  console.log("This message appears after 2 seconds.");
}, 2000);

console.log("End");
output
// press run to see the real timing

Why does "End" print before the delayed message? Node runs synchronous code on the Call Stack first, all the way through — so "Start" and "End" execute immediately, back to back. setTimeout() isn't handled by V8 at all; it's handed off to libuv the moment it's called, which starts a real 2-second timer in the background. Only once the timer finishes does libuv's result get queued, and only once the Call Stack is empty does the Event Loop move that callback onto the stack to run. That's why the "End" line — written before the callback even fires — always logs first.

Task 2 — Event Loop Demonstration

console.log("Program Started");

setTimeout(() => {
  console.log("Executing Delayed Task");
}, 0);

console.log("Program Finished");
output
// press run to see the real timing

How the Event Loop executes this: Even with a 0ms delay, setTimeout is still routed through libuv, not run in place. So "Program Started" and "Program Finished" — both plain synchronous lines — run to completion first. Only after the Call Stack is completely clear does the Event Loop check the timers phase, find the expired 0ms timer waiting, and push "Executing Delayed Task" onto the stack. A delay of zero still means "after the current script finishes," never "instantly."
